# AGENTS.md (components repo)

Rules for any AI coding agent working in the components repository. This repo holds the reference component set for the engine. Read the engine's `ARCHITECTURE.md` in the `yadad` repo (§9 Registry contract and ownership) first.

## Layout

```
components/
  sets/
    base/
      <name>/v1/     one folder per component: text, number, boolean, select, date,
                     reference, field-frame, section, panel, tabs, button, table,
                     calendar, board, count, error-summary
  registry/
    base.ts          maps each field type, layout piece and widget to exactly one component version
  UPSTREAM.md        source, upstream version and date copied, per component
```

## Hard rules

1. **Implement the contract, never change it.** Components import `@yadad/core` and `@yadad/testing` from the registry (`@yadad/core` is a peer dependency). If the contract is missing something, stop that part and say so in your report.
2. **Every registry entry passes the contract test kit** from `@yadad/testing`: renders with fixture options, emits the right JSON type on change, shows an error, passes axe.
3. **Versions live side by side.** A major upstream change means a new `vN` folder. Never edit an older version in place to track upstream. Switching versions is a one-line change in `registry/base.ts`.
4. **Attribution.** Copied or adapted code keeps its upstream license header and a source link, and gets a row in `UPSTREAM.md` (component, source URL, upstream version, date copied, notes).
5. **Accepted dependencies** are Radix (or React Aria / Base UI) for behavior primitives and TanStack Table / Virtual for tables. Anything else needs an engine-repo RFC.
6. **Styling is configurable by the host** (engine DECISIONS.md D15):
   - Read theme tokens (`--yadad-*` CSS variables from `@yadad/theme`). No hard-coded colors, spacing, radii or fonts.
   - Expose per-component variables that default to tokens, e.g. `--yadad-input-border: var(--yadad-color-border)`.
   - Give every rendered element a stable `data-part` (`data-part="input"`, `"label"`, `"error"`); hosts style against these, so renaming one is a breaking change.
   - Put all CSS in `@layer yadad.components` so unlayered host CSS always wins.
   - Plain CSS only: no Tailwind or other build-time CSS tooling. The repo ships pre-built CSS that hosts may import or skip.
7. **One component (one folder) at a time**, landed with its registry line and `UPSTREAM.md` row.
8. **Personal and work-specific notes go in `*.private.md` files** (gitignored, never committed). This covers employer or work-app names, clients, sign-off questions, and anything personal. Tracked files describe these generically and must not quote or summarize `*.private.md` content.

## Landing and releasing

You land and release your own work. Nobody reviews or merges it for you.

- Commit straight to `main` and push (`origin` pushes to GitHub and the GitLab mirror together). Run `pnpm typecheck && pnpm test && pnpm build` before pushing. No PRs, no review requests. With several agents at once, use a worktree under `.worktrees/`, rebase on `origin/main` and push `HEAD:main` (fast-forward only, never force-push).
- `pnpm` may not be on `PATH`; use `corepack pnpm`. Node >= 22.18. `@yadad/core`, `@yadad/theme` and `@yadad/testing` are dev dependencies linked from a sibling `../yadad` checkout (`link:`); install there first, then here.
- `pnpm build` is `tsc -p tsconfig.build.json` plus `scripts/build-css.ts` (emits `dist/yadad-components.css`, exported as `./styles.css`).
- To release, add a changeset (`pnpm changeset`; patch for fixes, minor for features while pre-1.0), then run `pnpm changeset version` to bump the version and write `CHANGELOG.md`, and commit and push. The GitLab mirror's CI publishes any version the registry does not have yet (`scripts/release/publish.sh`) and skips publishing while changesets are pending.
- When the engine releases a new `@yadad/core` minor, widen the `@yadad/core` peer range to include it, check the gate, and release, so consumers never need an `overrides` workaround.

## Styling guardrails

`THEMING.md` is generated by `scripts/theming.ts` from the CSS and TSX; never hand-edit it. Regenerate with `pnpm theming:docs`. `scripts/theming.test.ts` (`pnpm theming:check`, part of `pnpm test`) fails if it drifts, or on a hard-coded color, a stray length, or CSS outside the layer. A README change needs no changeset (docs only); `THEMING.md` ships in the package, so a change to it caused by a behavior change rides on that change's changeset.

Phone tap targets must be at least 44x44 CSS px. 44 px cannot be a literal (length guardrail), so each tap-target component declares a token-derived variable (two `space-4` plus `space-3`, i.e. `calc(var(--yadad-space-4) * 2 + var(--yadad-space-3))`): `--yadad-button-tap`, `--yadad-field-frame-checkbox-tap` (checkbox label only, via `:has()`), `--yadad-table-sort-tap`, `--yadad-tabs-tap`, `--yadad-select-tap`.

## Real-browser checks

`pnpm gallery` serves a page that renders every registry entry in all of its states, with light, dark (the engine's `darkTheme`), stress (the gallery's own deliberately different dark tokens), brand and 100%/200% text toggles. Use it for any UI change (desktop and 390x844 with touch, keyboard-only).

`gallery/check/` holds rerunnable, unpublished checks that drive Chromium via `playwright-core` and exit non-zero on failure:

```sh
GALLERY_URL=http://localhost:5199/ node gallery/check/tabs-keyboard.ts
GALLERY_URL=http://localhost:5199/ node gallery/check/phone-touch.ts
```

If the machine's Chromium differs from the one `playwright-core` ships, set `PLAYWRIGHT_EXECUTABLE_PATH=/path/to/chrome-headless-shell`.

- `tabs-keyboard.ts`: at 200% text the long tab list scrolls internally instead of forcing page-level horizontal overflow; `End` reaches the last tab with its focus ring inside the viewport; the tablist's ring-clearance padding covers the focus-ring extent in both themes at both sizes.
- `phone-touch.ts`: at 390x844 and 320 px wide with touch, in both themes and at 200% text: tap targets (buttons, checkbox label, sortable headers, tabs, pickers) are at least 44x44; nothing forces the host page to scroll sideways; inputs render at 16 px or larger; the long tab list stays scrollable with the selected tab visible; a real touch tap activates the button; the stacked phone table works (rows as cards, a column label on every cell, sort strip tap targets) and is a normal table at desktop width; section and panel pick up a shadow from the engine's shadow tokens. A native date control's intrinsic minimum width cannot be shrunk by CSS; if it is the only cause of page overflow it is reported as a documented limitation, not a failure.

## Keeping up with engine releases

`peerDependencies` declares which `@yadad/core` versions this set works with. Pre-1.0, every new core minor falls outside a `^0.x.0` range, so hosts on the newest engine would get a peer conflict. Check with:

```sh
corepack pnpm check:engine
```

It asks the registry for every published `@yadad/core` and `@yadad/testing` version, reports the newest, and exits non-zero if the declared range does not cover it (or if the newest testing kit cannot run the kit against that core).

- The engine registry is LAN-internal, so GitHub's public runners cannot reach it. From there the script skips loudly (`SKIP ... This is NOT a pass.`) and exits 0; the GitHub `engine-range` job is a documented no-op. A reachable-but-stale range still fails.
- The verdict comes from the `engine-range` job in `.gitlab-ci.yml`: `k8s` runner, default-branch pushes, `.post` stage after `release`, `allow_failure: true`, using only CI variables (`CI_API_V4_URL`, `CI_JOB_TOKEN`, `CI_SERVER_URL`) and `pnpm check:engine --install`. A stale range shows as a pipeline warning.
- Widening needs proof: `corepack pnpm check:engine --install` copies the repo to a temp dir, swaps the `link:` dev dependencies for the newest published `@yadad/core`/`@yadad/testing`, installs, and runs the full gate. Only a passing run justifies adding the minor to `peerDependencies` (existing `^0.1.0 || ^0.2.0 || ...` style) plus a patch changeset. If it fails, the range stays: it is a component bug to fix or a contract change to report.

## Commit messages

[Angular format](https://github.com/angular/angular/blob/main/contributing-docs/commit-message-guidelines.md), enforced by `.githooks/commit-msg` (enable with `git config core.hooksPath .githooks`). Same rules as the engine repo's `AGENTS.md`, except the scope is the component name (`text`, `data-table`), `registry`, `dev-infra` or `deps`. Commit early and often: one logical step per commit.

## Done when

- Contract kit passes for the entry.
- `registry/base.ts` references it.
- `UPSTREAM.md` row present (if anything was copied).
- Showcase renders the matching fixture without engine changes.

## How to add a component

1. Add `sets/base/<name>/v1/` with the component(s) and a `<name>.css`.
2. Register it in `registry/base.ts` (fields get `Input`/`Display`; layout and widgets as appropriate).
3. Add a `UPSTREAM.md` row if anything was copied or adapted.
4. Make the contract kit pass for the entry.
5. One component per commit, scope = the component name.
